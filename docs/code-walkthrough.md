## 2. Where is `main`?

In C, a program always starts at `int main()`. **Python has no mandatory start function**: it
runs the file you give it from top to bottom. By convention you write a `main()` function and
call it from this block at the end of the file:

```python
if __name__ == "__main__":
    sys.exit(main())
```

This project has **two entry points**:

| Command | What starts | Where it begins |
|---|---|---|
| `uv run python -m job_analyzer.analyze capture.txt` | The CLI | [job_analyzer/analyze.py](../job_analyzer/analyze.py), the `if __name__ == "__main__"` block → `main()` |
| `uv run pytest` | The tests | pytest finds `tests/test_*.py` and runs every `test_*` function |

The other modules (`trim`, `ranking`, `rules`, `models`) are **libraries**: they have no `main`
and never run on their own. They are only imported.

## 3. Startup sequence, step by step

What happens when you type:

```bash
uv run python -m job_analyzer.analyze tests/fixtures/synthetic_external.txt --trim-only
```

1. **`uv run`** finds the project's `.venv` and runs its `python.exe`, so the libraries
   installed there (anthropic, pydantic…) are used, not the system ones.
2. **`-m job_analyzer.analyze`** tells Python: "find the *module* `analyze` inside the
   *package* `job_analyzer` and run it as the main program". `-m` is used instead of
   `python job_analyzer/analyze.py` so that `from job_analyzer.xxx import ...` works the same
   from anywhere.
3. Python imports the package first → runs [job_analyzer/\_\_init\_\_.py](../job_analyzer/__init__.py)
   (it only holds a docstring).
4. Python runs `analyze.py` **top to bottom**, with the special variable
   `__name__ = "__main__"`:
   - **The `import` lines.** Each imported module runs completely, *once*: `models.py` creates
     the `JobPosting` class, `trim.py` compiles its regexes, and so on. A later import of the
     same module reuses the one already loaded.
   - **The constants** (`MODEL`, `ROOT`, `INSTRUCTIONS`) are computed.
   - **`def` and `class` only register; they do not run.** Like declaring a function in C:
     it exists, but nobody has called it yet.
5. It reaches the bottom: `if __name__ == "__main__":` is true → it calls `main()`.
6. `main()` reads the arguments, processes the capture and returns `0` (success) or `1` (error).
7. `sys.exit(0)` ends the program with that exit code; PowerShell stores it in `$LASTEXITCODE`.

> **Why `if __name__ == "__main__"` exists:** when the tests do `from job_analyzer import analyze`,
> the file also runs top to bottom, but with `__name__ = "job_analyzer.analyze"`. The `if` is
> false and `main()` does **not** run. Without it, importing the module to test it would start
> the whole CLI.

## 4. Block diagram: data flow

```text
 capture.txt  (raw F9 text: URL line + full page with noise)
      │
      ▼
 ┌────────────────────┐   job_id, canonical url, search query
 │  extract_url_info  │───────────────────────────────────────► printed (phase 2 → database)
 │  trim.py           │
 └────────────────────┘
      │ raw text (the URL line is still there)
      ▼
 ┌────────────────────┐
 │  trim_page         │   keeps ~30–55% of the text: only the open posting
 │  trim.py           │
 └────────────────────┘
      │ clean posting
      ▼
 ┌──────────────────────────────────────────────┐
 │  analyze()   analyze.py                      │
 │                                              │        ┌─────────────────┐
 │  system = INSTRUCTIONS + criteria.md         │ ─────► │  Claude API     │
 │  user   = clean posting                      │  HTTPS │  (Sonnet 5.5)   │
 │  format = JobPosting as JSON Schema          │ ◄───── │                 │
 │                                              │  JSON  └─────────────────┘
 │  JSON → JobPosting object (Pydantic checks)  │
 │  validate_posting(): scores within 1–5       │
 └──────────────────────────────────────────────┘
      │ posting: JobPosting
      ├───────────────────────────► initial_status()  ──► "discarded" | "to_review"
      │                              rules.py
      ├──► days_since_posted() ──► days ──┐
      │    ranking.py                     ▼
      └──────────────────────────────► priority()  ──► number (higher = review first)
                                        ranking.py
```

**The key design idea:** the LLM only does what fixed rules cannot do, which is reading free
text and extracting data. Everything that must be predictable is done by Python: trimming,
converting dates, discarding and ranking. It is the same split as in a safety system: the
sensor (the LLM) supplies data, and the decision logic is deterministic and verifiable.

## 5. Who calls whom (call graph)

```text
main()                                      analyze.py
├── ArgumentParser.parse_args()             standard library: reads the command line
├── Path.read_text()                        reads capture.txt
├── extract_url_info(text)                  trim.py
├── trim_page(text)                         trim.py     ← only to print the trim %
├── [if --trim-only] print(...) → return 0
├── CRITERIA.exists()                       fails early if config/criteria.md is missing
├── load_dotenv(ENV_FILE)                   python-dotenv: loads ANTHROPIC_API_KEY from .env
├── os.environ.get("ANTHROPIC_API_KEY")     fails early if the key is missing (never prints it)
├── analyze(text)                           analyze.py
│   ├── Anthropic()                         SDK: creates the HTTP client
│   ├── system_prompt()                     analyze.py → reads config/criteria.md
│   ├── trim_page(text)                     trim.py     ← the text actually sent to Claude
│   ├── client.beta.messages.parse(...)     SDK → network → Claude API
│   └── validate_posting(posting)           rules.py
├── days_since_posted(posting.posted_ago)   ranking.py
├── initial_status(posting)                 rules.py
└── priority(posting, days)                 ranking.py
    ├── fit(posting)
    └── opportunity(posting, days)
        └── recency_weight(days)
```

`trim_page()` is called twice on purpose: `analyze()` takes the raw text and trims it itself.
That way, in phase 2, the background worker can call `analyze(text)` directly, without
depending on `main()`.

### Module dependencies (who imports whom)

```text
                 analyze.py   ← entry point; imports everything
               /     |     \       \
          trim.py  ranking.py  rules.py
                        \        /
                        models.py   ← base: imports nothing from the project
```

`trim.py` and `models.py` depend on nothing else in the project. Arrows only point downwards
and there are no cycles (A imports B and B imports A). That is what allows testing each piece
on its own.

## 6. Module by module

### 6.1 `trim.py` — text cleanup (no AI)

| Function | Input | Output | What it does |
|---|---|---|---|
| `trim_page(text)` | raw text | trimmed text | Keeps what lies between `LinkedIn Corporation ©` and the first end marker found in `END_MARKERS` (one per LinkedIn layout). If a marker is missing, it returns everything (fallback). |
| `extract_url_info(text)` | raw text | `UrlInfo` | Finds the `URL:` line added by F9 and extracts the job ID and the `keywords` parameter. |

Python concepts used here: **regex** (`re.compile`, `.search`, `.group`), **immutable
dataclass** (`@dataclass(frozen=True)`), **slicing** (`text[a:b]`), **conditional expression**
(`X if cond else Y`) and **`a or b`** as a default value.

What the regex returns for the synthetic capture's URL:

```text
URL: https://www.linkedin.com/jobs/search-results/?currentJobId=4123456789&...&keywords=Senior%20System...
                                                                 └────┬───┘
JOB_ID_RE.search(...).group(1)  →  "4123456789"   (group 1 = what is inside the parentheses (\d+))
```

### 6.2 `models.py` — the job card schema

`JobPosting` does two jobs:

```text
        class JobPosting(BaseModel)
         │                       ▲
         │ SDK: to_json_         │ Pydantic: checks types and
         │ output_format()       │ builds the object
         ▼                       │
   JSON Schema  ──► API ──►  Claude's JSON
   {"type":"object",          {"company":"ALTEN",
    "properties":{...},        "visa":"not_applicable", ...}
    "required":[...]}
```

- `Literal["a", "b"]` = closed enum. Claude **cannot** answer a value outside the list; the API
  guarantees it.
- `Field(description=...)` = an instruction for Claude about that field. It travels inside the schema.
- `str | None` = the field may be empty (`null` in JSON).

### 6.3 `rules.py` — hard decisions

| Function | What it does |
|---|---|
| `validate_posting(p)` | Raises `InvalidPosting` if a score is outside 1–5. Needed because the API does not support `minimum`/`maximum` in the schema. |
| `initial_status(p)` | `"discarded"` if it requires clearance/ITAR or citizenship, or if it only accepts local candidates outside Mexico; otherwise `"to_review"`. `"no_sponsorship"` does **not** discard (TN option). |

### 6.4 `ranking.py` — priority

```text
priority = fit                                + opportunity                      + location
         = 0.5·domain_similarity              + recency_weight + signals         + 0.3·(loc − 3)
           + 0.4·technical_match
           range 0.9 … 4.5                     range −0.4 … 1.2                   ±0.6 (phase 4)
```

**Worked example.** A posting with `domain_similarity=5`, `technical_match=4`, posted 2 days
ago, with "Actively reviewing applicants":

```text
fit         = 0.5·5 + 0.4·4            = 2.5 + 1.6 = 4.1
opportunity = recency_weight(2) + 0.2 (actively_reviewing)
            = 0.5 + 0.2                = 0.7
priority    = 4.1 + 0.7                = 4.8      (location: None → neither adds nor subtracts)
```

`days_since_posted()` is a small parser: a regex finds *number + unit* ("2 days",
"una semana") and a dictionary turns the unit into days.

### 6.5 `analyze.py` — orchestration and the Claude call

`analyze()` builds the request from these parts:

| Parameter | What it is |
|---|---|
| `model` | `claude-sonnet-5-5` (change it with `--model`) |
| `system` | Fixed instructions + `criteria.md`, marked with `cache_control` so it is not paid in full every time |
| `messages` | A single user message: the trimmed posting |
| `output_format=JobPosting` | Structured output: the answer **must** match the schema |
| `output_config={"effort": "medium"}` | How much the model reasons; `medium` is enough for extraction |
| `fallbacks="default"` | If a safety classifier declines by mistake, the API retries on another model |

Then it checks `stop_reason`, which says why the model stopped:

```text
"end_turn"   → normal: there is a job card
"refusal"    → declined   → AnalysisError
"max_tokens" → cut off    → AnalysisError
```

### 6.6 How the API key is handled

```text
 .env  (git-ignored, on your disk only)
   │  load_dotenv(ENV_FILE)
   ▼
 os.environ of THIS process only   ← not a Windows-wide variable
   │  Anthropic() reads ANTHROPIC_API_KEY
   ▼
 HTTPS header to the Claude API    ← never printed, never logged
```

- `main()` checks that the key exists **before** calling the API and explains how to fix it.
- API errors are reported by type (rejected key, HTTP status, connection) and never echo the key.
- `tests/test_repo_safety.py` fails if `.env` or any personal file stops being git-ignored.

## 7. The tests

```text
uv run pytest
   │
   ├─ test_trim.py         (12)  trim_page() with both marker variants, fallback,
   │                             job_id/keywords, bare link, side-list protection
   ├─ test_ranking.py      (37)  days_since_posted() with 23 formats, recency_weight boundaries,
   │                             signals, location, initial_status, validate_posting
   ├─ test_analyze.py      (8)   Claude call with a FAKE client (no network, no cost),
   │                             schema compatibility, CLI preconditions (criteria, API key)
   └─ test_repo_safety.py  (6)   secrets and personal files stay git-ignored
```

**The fake client** is the same idea as SIL: the code under test does not know whether it
talks to the real system or to a model.

```text
  Production                           Test
  ──────────                           ────
  analyze(text)                        analyze(text, client=FakeClient(...))
      │                                    │
      ▼                                    ▼
  Anthropic().beta.messages.parse      FakeClient.parse
      │                                    │  stores the arguments in self.kwargs
      ▼                                    │  returns a prepared response
  network → Claude API                     ▼
                                       the test checks kwargs with assert:
                                       right model? trimmed text sent?
                                       cache marked? JobPosting schema requested?
```

This works because `analyze()` accepts `client=None` as a parameter (*dependency injection*).
If you pass no client, it creates the real one.

**`@pytest.mark.parametrize` = test vectors.** The same test runs with several inputs and
expected outputs. Adding a case means adding one line to the table.

**`monkeypatch`** temporarily replaces a variable, a function or an environment variable during
one test and restores it afterwards. `test_main_without_api_key_fails_before_calling_the_api`
uses it to remove the key, point `.env` to a file that does not exist, and replace `analyze()`
with a function that fails the test if it is ever called.

## 8. Syntax glossary (in order of appearance)

| Syntax | Meaning | Example in the code | C equivalent |
|---|---|---|---|
| `"""text"""` at the top of a file/function | *docstring*: documentation Python stores in `__doc__` | top of every module | Doxygen comment |
| `import x` / `from x import y` | loads a module (runs it once) | `from job_analyzer.trim import trim_page` | `#include` + linking |
| `NAME = value` in upper case | constant by convention | `START_MARKER` | `#define` / `const` |
| `(a, b)` | *tuple*: a list that cannot be modified | `END_MARKERS` | `const` array |
| `def f(x: str) -> int:` | function with *type hints* (Python does not enforce them; tools check them) | `def trim_page(text: str) -> str:` | `int f(char* x)` |
| `x: str \| None` | either `str` or `None` | `job_id: str \| None` | pointer that may be `NULL` |
| `def f(x, y=None)` | parameter with a default value | `analyze(text, model=MODEL, client=None)` | overloading |
| `r"..."` | *raw string*: `\` is not an escape | `r"(\d+)"` | — |
| `f"...{x}..."` | inserts variables into text | `f"{field}={value}"` | `sprintf` |
| `text[a:b]` | *slicing*: substring from a to b−1 | `trim_page()` | `strncpy` with an offset |
| `X if cond else Y` | conditional expression | `m.group(1) if m else None` | `cond ? X : Y` |
| `a or b` | `a` if truthy, otherwise `b` | `client or Anthropic()` | `a ? a : b` |
| `@decorator` | function that modifies the class/function below it | `@dataclass(frozen=True)` | — |
| `class A(B):` | class inheriting from B | `class JobPosting(BaseModel)` | `struct` + C++ inheritance |
| `Literal["a","b"]` | only those values | `Signal` | `enum` |
| `{key: value}` / `.items()` | dictionary and its pairs | `_DAYS_PER_UNIT` | lookup table |
| `for k, v in d.items():` | iterates pairs and *unpacks* them | `days_since_posted()` | `for` over an array of structs |
| `for …:` + `break` | leaves the loop as soon as something is found | `trim_page()` | `break` |
| `x in some_list` | membership test | `"top_applicant" in p.linkedin_signals` | linear search |
| `1 <= v <= 5` | chained comparison | `validate_posting()` | `1 <= v && v <= 5` |
| `raise E(...)` / `try: … except E:` | throw / catch errors | `AnalysisError` | error return codes |
| `except (A, B) as e:` | catch several error types in one branch | `main()` | — |
| `**kwargs` | receives keyword arguments in a dict | `FakeClient.parse(**kwargs)` | `va_list` |
| `{**a, **b}` | merges dictionaries (b wins) | `posting(**changes)` in tests | — |
| `lambda p: p.name` | one-line anonymous function | `ids=lambda p: p.name` | function pointer |
| `with X:` | block with controlled entry/exit | `with pytest.raises(...)` | — |
| `Path(...) / "x"` | joins paths | `ROOT / "config" / "criteria.md"` | `snprintf` of paths |
| `if __name__ == "__main__":` | runs only when this is the main program | bottom of `analyze.py` | `main()` |

## 9. Learn-by-doing exercises

From easiest to hardest. Run `uv run pytest` after each change.

1. **Run without the API.** Save a real posting with F9 into a `.txt` and run
   `uv run python -m job_analyzer.analyze your_file.txt --trim-only`.
   What percentage of the text was kept? Does the trimmed text start at the right title?

2. **Use the debugger.** In VS Code, open the *Testing* panel (flask icon), find
   `test_external_apply_variant`, set a *breakpoint* (click left of the line number) inside
   `trim_page()` in `trim.py` and choose **Debug Test**. Step with `F10` and watch `start` and
   `end` in the variables panel. It is the best way to see "who calls whom".

3. **Break a test on purpose.** In `trim.py`, change the first item of `END_MARKERS` to the long
   version `"See how you compare to other applicants"`. Which tests fail and why? (It is the real
   bug found with 2 of the 4 first real captures.) Put it back afterwards.

4. **A coverage question.** Change `0.5` to `0.6` in `fit()`. Does any test fail? What does
   that say about what the tests cover? Write a test that catches it.

5. **TDD (test first).** LinkedIn sometimes abbreviates: `"2d ago"`, `"3w ago"`. Add those
   cases to the `test_days_since_posted` table, confirm they fail, then adjust `_QUANTITY_RE`
   and `_DAYS_PER_UNIT` until they pass without breaking the others.

6. **A new hard rule.** Add a discard to `initial_status()` for a language you do not speak
   (e.g. mandatory German), with its case in `test_initial_status`.
